# 真实数据使用规则

日期：2026-10-15。任务：K001。适用于所有参与者：人、AI agent、CI。

## 先看这条

**现在（G1 之前）只能用合成数据。** 不要把真实密码库、真实密码、真实私钥、真人证件号放进本仓库、测试设备、CI、截图，或任何 AI agent 的对话和工具输出里。

为什么连 agent 也不行：agent 执行命令的输出会发到模型服务商——这就是“发给了第三方”，发出去就收不回。

## 1. 什么算真实数据

满足任一条就算，**不管有没有加密**：

| 类型 | 例子 | 为什么算 |
| --- | --- | --- |
| 真实可用的凭据 | 你自己任何网站的密码、OTP 种子、恢复码、Passkey | 能直接登录 |
| 真实密码库文件 | 日常在用的 `.kdbx` 及其备份 | 要测就得解锁；密文本身也给了离线猜主密码的机会 |
| 真实私钥 | 能登录真实服务器的 SSH 私钥、签名证书 | 能直接冒充你 |
| 真人个人信息 | 证件号、手机号、银行卡号（包括过期卡） | 泄露后不可撤回 |
| 真实账号的同步凭据 | OneDrive token、WebDAV 密码、上传会话 URL | 能读写、删除你的云端文件 |
| 从以上任一项衍生的东西 | 导出的 CSV、截图、日志片段、崩溃转储 | 和来源一样敏感 |

## 2. 合成数据怎么造

- **域名**只用保留域名：`example.com`、`example.org`、`*.example`、`*.test`、`*.invalid`。RFC 2606/6761 保证它们不会被第三方注册。注意 `example.com` 是 IANA 真在运行的网站，只适合不联网的样本；真要发请求的测试（Digital Asset Links、Related Origin、WebDAV）用 `*.test` 加本地解析指向自建服务。
- **标题和用户名**带“合成”或 `synthetic` 字样，一眼能认出来。
- **证件号、手机号、卡号不要随机生成“看起来很真”的号码**——随机号码可能正好属于某个真人。要用不可能存在的号码：
  - 证件号：不需要过格式校验时用 `TEST` 开头。需要过 18 位格式校验时，用不存在的行政区划码 `000000` 开头，配合法的出生日期，最后一位按 GB 11643 算校验码——否则会卡在格式校验，测不到后面的逻辑。
  - 手机号：样本库和截图里用 `100` 开头的 11 位数。大陆手机号都是 `13`–`19` 开头，`100` 不会是真号码，但也过不了 `1[3-9]` 格式校验。必须过这个校验的单元测试，在测试代码里现场生成，不写进样本库、证据和截图。
  - 银行卡号：用支付网关文档里通用的测试卡号（例如 `4111 1111 1111 1111`），或故意不通过 Luhn 校验的号码。
- **SSH 密钥**分两种。样本库里只测保留和解析的私钥，从公开种子派生（`tests/fixtures/kdbx/source.py`），等于公开，绝不能授权给任何主机。要真的登录或签名的密钥现场生成，只授权给一次性的测试虚拟机或容器，绝不加进真实服务器的 `authorized_keys`。
- **Passkey** 同理：样本库里的 Passkey 私钥也从公开种子派生，只测保留；要真的注册和登录，用自建测试 RP 或公开的 WebAuthn 测试站，配专门注册的测试账号。
- **合成库的主密码**可以写进证据文件（K002 要求这样做，方便别人复现）。正因为公开了，这个密码绝不能在任何真实地方复用。

## 3. 真实库分级接入

每升一级都要前一级的门槛证据已提交并经独立复核。

| 级别 | 允许做什么 | 前提 |
| --- | --- | --- |
| L0 合成（**当前**） | 只用合成库 | — |
| L1 真实库只读副本 | 在开发者本人设备上，用 keex 只读打开真实库的**副本** | G1 证据齐全（K020 完成）；该副本的写入闸门关闭；只用发布配置构建的 keex——调试构建带调试授权和详细日志（[THREAT_MODEL.md](THREAT_MODEL.md) T10） |
| L2 真实库写入 | 对真实库副本写入，即个人试用 | 达到 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) 的“个人试用版”门槛；只用发布配置构建；写之前另有一份用 KeePassXC 等其他客户端确认能打开的备份 |
| L3 日常主力 | 直接用 keex 管理主库 | 正式发布判定（G5）通过 |

**不管哪一级**，真实数据都不进仓库、CI、agent 会话、截图、问题跟踪器。

## 4. 日常做法

- `.gitignore` 已排除 `*.kdbx`、`*.key`、`*.ppk`、OpenSSH 默认私钥名（`id_ed25519` 等）。合成 KDBX 样本放在 `tests/fixtures/kdbx/`，来源和密码登记在同目录的 `manifest.json`，逐个用 `git add -f` 加入。`.gitignore` 只防手滑，不防故意。
- 给 agent 的任务只引用合成样本路径。不要让 agent“帮我打开我的库看看”。
- agent 在工具输出里看到疑似真实秘密时，立即停下并告诉用户，**不复述那个值**。
- 系统自动填充、Passkey 提供者、SSH 代理只在专用测试机、模拟器或测试用系统账户里启用。在日常使用的设备上启用，真实网站的保存请求和 Passkey 注册会被写进合成库，真实的 `git`/`ssh` 也会连到测试代理。
- 截图只截合成数据；截之前确认屏幕上没有真实通知、剪贴板预览或其他窗口。
- OneDrive、WebDAV、Passkey 测试账号专号专用，凭据存在开发者本机的系统钥匙串或密码管理器里，不进仓库，不提交 `.env`。
- 提交证据前至少人工搜一遍：非保留域名、`-----BEGIN` 开头的私钥块、长度像令牌的随机串。自动扫描脚本 K002 没有做，目前仍靠人工；做的时候注意 `tests/fixtures/kdbx/source.py` 里有 OpenSSH 私钥的头尾模板字符串，不是密钥。

## 5. 不小心泄露了怎么办

1. **停下**。不要继续复制、粘贴、提交。
2. **当作已经泄露**。从 git 历史里删、清空对话都撤不回来——已经推送、同步或发给模型服务商的，就当别人已经有了。
3. **去源头作废**。改密码、吊销 token、重新生成密钥并从 `authorized_keys` 移除、联系发卡行。这一步才是真正的补救。
4. **清理本地痕迹**。从工作区、未推送的 git 历史、临时目录中删除。
5. **记录**。在对应任务的 `adr/evidence/` 文件里写时间、类型、处理结果，**不写泄露的值本身**。
