## 1. 一句话结论

以下对密文、锁库与手机防护的承诺以客户端执行代码可信为前提。Web 还信任实际加载的构建、托管通道与浏览器；恶意同源代码可以在解锁时获取资料，不能宣传“用了KDBX/WASM就不必信任网页”，见 T15。

- **防得住**：只拿到密文文件的人（同步端、网络窃听者，以及被偷时已锁、且快速解锁只用硬件绑定封装的设备），在主密码足够强时读不到内容；被改过的密文会被拒绝，不会被写回把库弄坏（KDBX 3.1 有前提，见 T1）；锁库之后 keex 不再交出任何秘密或签名。
- **部分防**：手机上拿到无障碍、输入法或悬浮窗权限的恶意 App（T4a）。keex 能缩小它能看到、能点到的范围，但用户给了恶意 App 无障碍权限，它基本能看到用户看到的一切；恶意输入法能记下主密码。
- **不防**：已拿到 root/管理员/内核权限的攻击者、越狱或 Root 过的设备、胁迫用户、弱主密码被离线暴力猜中。

## 2. 要保护的资产

| 编号 | 资产 | 放在哪 | 失守会怎样 |
| --- | --- | --- | --- |
| A1 | 主密码、密钥文件 | 用户记忆/用户选的位置；解锁时短暂进入进程内存 | 整库失守 |
| A2 | 解密后的库内容：条目、受保护字段、附件 | 只在已解锁会话的内存里 | 秘密泄露 |
| A3 | 加密 `.kdbx`、加密备份、合并祖先快照 | 本机、同步端、备份位置 | 本身不直接泄露内容，但给了离线猜主密码的机会；损坏或丢失就是丢数据 |
| A4 | 库外可见的元数据：文件名、大小、修改频率、系统凭据索引里的账户名/RP ID、日志 | 文件系统、同步端、系统索引 | 暴露“你在哪些网站有账号” |
| A5 | 本机快速解锁材料 | Keychain、Keystore（【桌面】Windows Hello 等） | **等同主密钥**：拿到它就能打开同一主密钥下的所有副本、备份和同步端密文，不用猜。泄露后唯一补救是更换主密码或密钥文件 |
| A6 | 同步凭据：WebDAV 密码、OneDrive token、上传会话 URL | 系统安全存储；上传 URL 只在内存 | 别人能读写你的密文文件（读不到内容，但能删、能回滚） |
| A7 | **使用能力**：Passkey 断言、自动填充（【桌面】另有 SSH 签名） | 已解锁会话 + 授权状态 | 不用偷走私钥，也能冒充你登录 |
| A8 | 剪贴板里的值 | 系统剪贴板、剪贴板历史、跨设备剪贴板 | 被其他 App 或另一台设备读到 |
| A9 | 数据完整性：库不被 keex 自己写坏、不被同步静默覆盖 | — | 密码管理器最常见的“事故”其实是丢数据 |
| A10 | 金融/通信/证件资料、激活码、付款/恢复关系、规则与完成记录 | 加密KDBX；解锁后最小视图与内存索引 | 暴露个人服务关系、错误维护导致账户失联；资料错误不等于机构真实状态 |
| A11 | Web执行构建、浏览器会话、可选密文缓存与本机通知调度信息 | 可信静态部署、浏览器内存/密文存储、受设备保护的通知映射 | 构建被替换可窃取解锁材料；缓存丢失或时序元数据泄露 |

A7 最容易被忽略：攻击者不需要拿到私钥或密码，只要能让 keex 替他签一次名、填一次密码就够了——手机上借无障碍服务代点的恶意 App（T4a）就能这么做；【桌面】同用户进程（T4b）和你转发过 SSH 代理的远端主机（T14）也能。所以“私钥没离开 keex”不等于“安全”。

## 3. 信任边界

```text
┌──────────────── 用户的手机 ────────────────┐
│ keex 主程序 · 原生凭据扩展                   │ 解锁后可持有秘密，彼此用 epoch 协调
│ 系统安全存储 · 系统凭据框架 · 浏览器          │ 部分可信：按协议、签名、来源校验
│ 其他 App（可能是恶意的）                     │ 不可信；沙箱隔离，但能借无障碍、输入法、悬浮窗
└──────────────────────────────────────────┘
      │ 只传密文                      │ 只回应经过校验的请求
 同步端（WebDAV/OneDrive）       网站、调用方 App
 不可信                          不可信

 OS 内核、root、越狱 —— keex 依赖它，防不住它
```

【桌面】未来桌面应用还多出 SSH 代理、浏览器桥接、同一系统用户下的其他进程，以及经 `ssh -A` 转发来的远端，见 T4b、T14。

**信任**：OS 内核与沙箱；硬件绑定的系统安全存储；系统凭据框架对调用方身份的认证（Android 包签名、Apple 系统传入的请求参数）；经审查的密码学库。

**有条件信任**：用户在 keex 界面上的确认操作——前提是没有别的程序能替用户点击。手机上见 T4a（无障碍服务、悬浮窗），桌面见 T4b。

**不信任**：同步端和网络；网站；调用方自己声明的包名、域名、页面标题；导入的文件；其他 KDBX 客户端写回的内容；其他 App；【桌面】同用户的其他进程，以及用户目录下 keex 自己的普通配置文件（同用户进程能改）。

**Web 独立边界**：浏览器运行时与实际加载的前端代码必须可信；同步服务器不因此成为可信解密方。Worker/WASM、IndexedDB、同源标签均不是抵挡同源恶意脚本的秘密隔离层。可信静态包由用户选择的部署交付，构建/托管通道被控制的残余风险见 T15。资料扩展不增加支付、充值或原生eSIM操作的授权边界。

## 4. 攻击者

每节的“验收”指向 [ACCEPTANCE.md](ACCEPTANCE.md) 的条目和 [TASKS.md](TASKS.md) 的任务。编号只增不改，新增的攻击者排在末尾。

### T1 恶意或被攻破的同步端

包括 WebDAV 服务器作恶、OneDrive 账号被盗、服务商内部人员。

**它能做**：拿到所有历史密文；回滚到旧版本；篡改或截断；删除；用 HTML 登录页冒充文件；忽略 `If-Match` 条件；跳转到别的域名骗认证头；返回超大文件或 XML 炸弹拖垮客户端。

**承诺**：

- 密文被改动就拒绝打开，不合并、不写回。具体靠什么，按格式版本不同：
  - **KDBX 4.x**：头部 HMAC + 逐块 HMAC。HMAC 只覆盖到结束块为止，结束块之后多出来的字节要 keex 自己检查并拒绝。
  - **KDBX 3.1**：没有 HMAC，只有不带密钥的块哈希和 XML 里可选的 `HeaderHash`。3.1 的内层流密钥和算法放在明文外层头里；没有 `HeaderHash` 时，同步端改了这两个字段不会被发现，受保护字段会解成乱码，keex 一保存就把乱码永久写回。所以 `HeaderHash` **对不上就拒绝打开**（和 KeePass、KeePassXC 一样按文件损坏处理）；**缺失时只读打开、不写回**，并提示用户可以在备份后显式升级到 4.1。
- 远端变化不会静默覆盖本地或远端；服务器不支持可靠版本条件时进入冲突副本模式（[ADR-0003](0003-cloud-sync.md)）。
- 认证头不跟随跨源跳转；TLS 错误默认拒绝；响应大小和 XML 深度有上限。
- 同步端拿不到主密码和快速解锁材料——这些从不上传。用户把密钥文件放在库旁边或同一个同步目录时，keex 要明确提醒：这样同步端手里就同时有了密文和密钥文件，只剩主密码一道防线。

**不承诺**：

- **弱主密码挡不住离线暴力破解。** 同步端可以无限次猜，KDF 只是让每次猜测更贵。说白了：密文一旦上传，就当它永远在别人手里，主密码强度是最后一道防线。
- 没有本地可信版本记录的新设备，首次同步时认不出远端给的是旧版本。有记录的设备可以发现“版本倒退”（K036 实现）。
- 可用性：对方能删文件、能拒绝服务。keex 只保证本地副本和加密备份还在。
- 元数据：文件大小、修改时间与频率、访问 IP。
- 换了主密码，同步端手里的旧密文仍能用旧主密码打开，无法远程撤销。

**验收**：AC-SYNC，AC-KDBX 错误案例；K015、K035、K036、K040、K041；M07。

### T2 被偷或丢失的设备

结果取决于被拿走那一刻的状态：

| 拿走时 | 攻击者手里有 | 承诺 | 不承诺 |
| --- | --- | --- | --- |
| 关机或设备锁屏，keex 已锁 | 磁盘上的密文；系统安全存储里的快速解锁材料 | 不经主密码或设备认证打不开；keex 不往磁盘写明文缓存、明文搜索索引、敏感页面的任务快照；快速解锁材料由**硬件绑定密钥**封装，不能被拷出来离线猜。算硬件绑定的条件：Apple 用 data protection keychain 加 `ThisDeviceOnly` 访问级别（否则会进加密备份、跟着迁机）；Android 的 Keystore 密钥要求 `AUTH_BIOMETRIC_STRONG`、经 `CryptoObject` 使用，并确认在安全硬件里（API 31+ 用 `KeyInfo.getSecurityLevel()` 只接受 TEE/StrongBox；`isInsideSecureHardware()` 已弃用，仅 API 30 及以下回退使用）。**达不到的设备不提供快速解锁**（AC-SECRET）。【桌面】Windows Hello 要有 TPM 支撑；Linux Secret Service、仅用 DPAPI、没有 TPM 的 Windows Hello 都只是软件封装，拿到磁盘就能按系统登录密码离线猜，会话解锁后同用户进程还能直接读出 | 取证工具利用系统漏洞绕过锁屏（归 T5） |
| 设备已解锁，keex 已锁 | 上面全部，外加能操作设备 | 进 keex 和响应系统凭据请求都要再认证 | 见下方“设备密码与重新录入” |
| 设备已解锁，keex 未锁 | 屏幕上能看到的一切 | 闲置、切后台、系统锁屏后自动锁库（K019）；秘密默认遮罩 | 自动锁库之前能看、能复制、能填充的内容 |

**设备密码与重新录入**：知道设备锁屏密码的人有两条路打开快速解锁——直接用设备密码回退，或者先在系统设置里录入自己的指纹或面容。所以“不允许设备密码回退”只有同时绑定“当前已录入的生物特征集合”才成立：

- iOS/macOS：Keychain 访问控制用 `.biometryCurrentSet`。
- Android：密钥设 `setInvalidatedByBiometricEnrollment(true)`，并用 `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`，即每次使用都认证。前提别漏：官方说明这项失效只对**没有设正数有效期**的密钥生效；设了 N 秒有效期，新录入指纹后密钥不会失效，本条承诺就不成立。
- 【桌面】Windows Hello：能否禁止 PIN 回退、新增指纹会不会让密钥失效，待实测。确认之前一律按“PIN 始终可以回退”对待。

K018 必须选定方案并在设置页写清后果：允许回退，就等于“知道你设备锁屏密码的人能开库”。

另外不承诺擦除残留：曾显示或导出过的明文可能留在 SSD、交换分区、休眠文件或系统崩溃转储里。

**验收**：AC-SECRET；K018、K019。

### T3 锁库竞态

这不是某个外部攻击者，而是时序问题：锁库那一刻正好有填充请求、Passkey 断言或保存在进行（【桌面】还有 SSH 签名）。攻击者可能故意卡在这个时间窗口。

**承诺**：锁库生效后，新请求和还没输出的在途请求一律拒绝；取消或失败的解锁不能让旧会话复活；扩展进程（【桌面】还有代理进程）在下一次处理请求前一定先看到撤权。完整规则见 §5。

**不承诺**：已经交出去的收不回——已填进网页的密码、已返回的签名、已被别的 App 读走的剪贴板内容。

**验收**：AC-SECRET 前两段；K012、K019、K038（【桌面】K044、K047）。

### T4 设备上的恶意 App 与同用户进程

分两种情况：手机上的恶意 App（T4a，当前范围）；桌面上同一系统用户的恶意进程（T4b，【桌面】资料）。

#### T4a 手机上的恶意 App

没有 Root/越狱时，应用沙箱让别的 App 读不到 keex 的私有目录和内存。恶意 App 能利用的是系统开放的接口：

| 途径 | Android | iOS |
| --- | --- | --- |
| 无障碍服务 | 用户授权后能读屏幕内容、替用户点击（包括 keex 的确认按钮），还能读到被填进别的 App 的密码 | 第三方 App 没有对等能力 |
| 输入法 | 第三方输入法能看到输入的一切，包括主密码 | 安全文本框上系统强制使用系统键盘；普通文本框里输入的秘密（例如手动输入的卡号）第三方键盘看得到 |
| 悬浮窗 | 有悬浮窗权限的 App 能盖住 keex 界面，诱导用户点击 | 不允许第三方悬浮窗 |
| 剪贴板 | Android 10+ 后台读不到；前台 App 和默认输入法能读 | iOS 16+ 读取别的 App 写入的内容会弹授权 |
| 通知 | 用户授予“通知使用权”的 App 能读所有通知的全文 | 第三方 App 读不到别的 App 的通知 |
| 外部调起 | 任何 App 都能用 Intent、链接、分享把 `otpauth://` 或 `.kdbx` 交给 keex | 同左，经 URL scheme 或分享 |
| 伪造调用方 | 见 T6 | 见 T6 |

**承诺**（候选措施，K019 实测后才算数；具体 API 版本见 [CAPABILITIES.md](CAPABILITIES.md) §2）：

- 显示秘密的界面、主密码输入框、确认和授权按钮在 Android 14+ 标记为无障碍敏感数据。标记后，没声明为无障碍工具的服务既读不到也点不了这些控件，TalkBack 这类工具不受影响。Flutter 是单一视图渲染，能否按控件生效要实测；不能就整页标记。
- 确认、显示秘密、复制等敏感界面过滤被遮挡时的点击；Android 12+ 隐藏其他应用的悬浮窗。
- 主密码输入框用系统的密码输入类型：iOS 用安全文本框（强制系统键盘）；Android 标密码类型并要求输入法不做个性化学习。iOS 另提供一个可选项：在整个 keex 里禁用第三方键盘，代价是搜狗等输入法在 keex 里都用不了。
- keex 自己发的通知（到期提醒、同步状态）只写类型和数量，不写条目标题、账户名和号码。
- 被外部调起时，先显示要做什么（添加哪个动态口令、打开哪个文件），用户确认后才写库，不自动导入。
- keex 自己不申请无障碍服务、悬浮窗权限，不做自定义键盘来实现填充（[ADR-0002](0002-mobile-credentials.md) §4）。
- 剪贴板使用平台的敏感内容标记，并限时清除（K019）。

**不承诺**：

- Android 上已获无障碍权限、且声明为无障碍工具的恶意服务（Android 14 以下则是任何无障碍服务）读屏幕和代点。“是不是工具”是服务自己声明的，只靠 Google Play 审核和 Play Protect 约束；没有 Google 服务的国内机型基本没有这层约束。说白了：用户给了恶意 App 无障碍权限，它基本能看到用户看到的一切。
- 无障碍服务自己的覆盖层**不会**被“隐藏其他应用的悬浮窗”一起隐藏：AOSP android14 源码中 `setHideOverlayWindows` 只隐藏系统悬浮窗类型（TYPE_APPLICATION_OVERLAY 等）和 TYPE_TOAST，不含 TYPE_ACCESSIBILITY_OVERLAY（`WindowManager.isSystemAlertWindowType`、`WindowState.setForceHideNonSystemOverlayWindowIfNeeded`）。K019 只做真机确认。
- 已获通知使用权的 App 读到其他 App（包括网站和银行发来的验证码短信）的通知。
- Android 上恶意输入法记下主密码；iOS 上第三方键盘看到普通文本框里输入的秘密。

**验收**：AC-SECRET；K019、K028、K048。

#### T4b 桌面上同一系统用户的恶意进程【桌面】

典型例子：用户装了一个带后门的命令行工具或浏览器插件，它和 keex 以同一个用户身份运行。

**它通常能做什么，取决于平台**：

| 平台 | 通常能做 | 通常做不到（靠 OS 保证） |
| --- | --- | --- |
| macOS | 读用户目录的大部分文件；连 keex 的 SSH socket；读剪贴板；拿到“辅助功能/输入监控”授权后记录键盘、替用户点击 | 附加调试启用了 Hardened Runtime 且不带调试授权（`get-task-allow`）的 keex——调试构建通常带这个授权，所以这条只对发布构建成立；读不属于它 access group 的 Keychain 项；部分目录受 TCC 授权弹窗保护 |
| Windows | 读用户文件；连 ACL 允许它访问的命名管道；全局键盘钩子；读剪贴板；用 `SendInput` 替用户点 keex 的确认按钮；在同用户、同完整性级别下读写 keex 进程内存或注入代码 | 碰其他用户或更高完整性级别的进程 |
| Linux（X11） | 键盘记录、截屏、读剪贴板、用 XTEST 替用户点击、连 socket；Yama `ptrace_scope` 为 0 时直接读 keex 内存；用下方的启动注入控制 keex | `ptrace_scope=1`（Ubuntu 默认）拦住附加非子进程，但挡不住启动注入。Flatpak 保护系统不被应用碰，不保护应用不被宿主上的同用户进程碰 |
| Linux（Wayland） | 读文件、连 socket；按 ptrace 设置可能读内存；用下方的启动注入控制 keex；装合成器扩展或改登录配置后，下次登录起可以记录键盘 | 当前会话里后台键盘记录和截屏（由合成器限制） |

**启动注入**：Linux 上同用户进程改掉 keex 的 `.desktop` 文件、自启动项或环境变量（如 `LD_PRELOAD`），keex 下次启动就带着它的代码运行，X11 和 Wayland 都一样。keex 装在用户可写位置时（Windows 按用户安装、Linux `~/.local`），它还能直接替换程序文件。所以下文的进程级保护只对**当前正在运行的实例**有效。

表中平台行为实施前按目标系统版本复测，结果记进对应任务的证据。

**承诺**（提高门槛，不是隔离）：

- SSH 签名默认每次在 keex 自己的界面确认，或在用户选定的有限时间内授权。这道确认只在 **macOS 发布构建（恶意进程没拿到辅助功能授权）和 Wayland** 上、对当前运行的实例算一道门槛；在 Windows 和 X11 上，同用户进程能替用户点击或直接注入 keex，按次确认只能防误用，挡不住有意的恶意进程。
- 每个密钥是否加入代理、按次还是限时，这些策略存进密码库本身（KeeAgent 本来就把每个密钥的设置放在条目里，受库的完整性保护）。必须存在库外的策略，用从库派生的密钥做 MAC，校验不过就按“每次确认”处理。不能放在没有保护的普通配置文件里——同用户进程直接改文件就能关掉确认，根本不经过 keex。
- 用户选“限时内不再询问”时，授权界面写明：这段时间内同用户进程和你转发过代理的远端主机（T14）都**可以**静默签名。
- 浏览器桥接用 native messaging 时只接受清单里登记的扩展 ID，并要求配对，不开放无认证的 localhost 接口。这能挡住网页、其他浏览器扩展和其他系统用户。
- keex 不主动把明文写盘。
- 减少内存被同用户读走的途径（候选措施，K019/K058 实测后才算数）：Linux 启动时调用 `prctl(PR_SET_DUMPABLE, 0)`——它同时挡住同用户的 ptrace 附加和读 `/proc/<pid>/mem`，也阻止生成同用户可读的 core 文件，比依赖 Yama 设置可靠——并把 `RLIMIT_CORE` 设为 0；Windows 用 `WerAddExcludedApplication` 把 keex 排除出系统错误报告。这些措施挡不住上面的启动注入。
- 剪贴板尽量使用平台的敏感内容标记，并限时清除（K019）。

**不承诺**：

- 库解锁期间读不到 keex 的进程内存。Windows 和 Linux 上都基本防不住：Linux 的进程级保护会被启动注入绕过。
- keex 装在用户可写位置时，程序文件本身不被替换。
- 防键盘记录：输入主密码时被记下来。
- 确认框能可靠告诉用户请求来自哪个进程。恶意进程可以掐准用户自己运行 `git push` 的时候插入一个请求，用户会以为是自己的。
- 浏览器桥接的配对挡住同用户进程——配对密钥就存在浏览器配置目录或 keex 配置里，native messaging 的清单文件同用户进程也能改。
- socket 文件权限 `0600` 只挡其他用户，挡不住同一用户。

**验收**：AC-SECRET 最后一段，AC-SSH；K005、K006、K045、K046、K050（均属未来桌面）。

### T5 root、管理员、内核与越狱/Root 设备

**不在防御范围。** 这类攻击者能读任意内存、挂钩系统 API、伪造用户确认，并在设备解锁后读取安全存储。

keex 不宣传能防住它们，也不把“越狱/Root 检测”当安全措施——检测容易被绕过，还会让用户误以为有保护。以后如果做检测，只能作为提示，文案里不能出现“已防护”。

恶意系统更新、被篡改的系统镜像同属此类。

### T6 钓鱼网站与伪装 App

**它能做**：同形域名（如用 Unicode 字符冒充拉丁字母）、子域名接管、在 iframe 里嵌入合法页面、伪造包名、在填充过程中途切换页面、重放旧的 challenge。

**承诺**：

- 自动填充和 Passkey 只依据**经过系统或浏览器认证的调用方身份**——Android 的包签名与 Digital Asset Links、Apple 系统传入的请求参数（【桌面】浏览器扩展核实的 origin 与 frame）。不按页面标题或调用方自报的字符串匹配。
- Android Autofill 结构里的 `webDomain` 是被填充的 App 自己报的，只有该 App 是验过签名的可信浏览器时才采信；其他 App 一律按包名 + 签名 + Digital Asset Links 匹配。否则任意 App 嵌一个网页就能拿到该网站的密码（AutoSpill 就是这类问题）。
- Passkey 私钥只为它所属的 RP 签名；RP 不匹配的请求不签。

**不承诺**：

- 用户手动复制密码粘贴到钓鱼页；合法网站自身被攻破（例如合法域名上的 XSS）；系统凭据框架自身的漏洞。
- 恶意 App 仿冒 keex 的解锁界面骗主密码。自动填充时 keex 本来就会在别的 App 上面弹解锁界面，用户很难分辨真假。keex 只能在引导里提醒：只在系统填充流程弹出的界面或 keex 自己里输入主密码；能用生物识别快速解锁时，主密码输入本身就少。

**验收**：AC-CREDENTIAL；K048、K049、K051–K053（K050、K054 属未来桌面）。

### T7 恶意输入文件

来源包括别人发来的 KDBX、导入的 CSV、附件、二维码里的 `otpauth://` 链接，以及其他 App 通过 Intent、URL scheme、分享交给 keex 的链接和文件（确认规则见 T4a）。

**它能做**：压缩炸弹、XML 实体与超深嵌套、超大 KDF 参数（让手机卡死或内存耗尽）、畸形 otpauth 参数、恶意附件。另外，keex 导出的 CSV 在 Excel 打开时，以 `=`、`+`、`-`、`@` 开头的字段可能被当成公式执行。

**承诺**：解析有大小、深度、数量上限；KDF 参数超出校准范围时先提示再执行，不让一个下载来的文件直接卡死设备；附件不自动执行，预览不调用外部程序；导入失败不覆盖已有数据。CSV 导出的公式转义由 K031 决定并测试。

**不承诺**：用户主动用外部 App 打开附件之后发生的事；用户自己从别的管理器导出的明文 CSV 留在磁盘上——keex 导入后提示删除，但不能替用户安全擦除。

**验收**：AC-KDBX 错误案例；K015、K024、K026、K030、K031。

### T8 网络窃听与中间人

**承诺**：默认不拉网站图标、不下载字体、不做泄露查询。TLS 严格校验，不降级到 HTTP，不忽略证书错误。keex 只在下表场景联网，**不在表里的联网都算缺陷**：

| 联网项 | 默认 | 会暴露什么 |
| --- | --- | --- |
| 用户配置的同步（WebDAV/OneDrive） | 关，配置后开 | 服务器地址、同步频率、文件大小 |
| Android 应用与网站的关联校验（Digital Asset Links：拉 `assetlinks.json` 或调 Google 的查询接口） | 启用 Android 系统填充或 Passkey 后，按需发生 | 你正在给哪个网站/应用填充 |
| 【桌面】浏览器扩展充当 WebAuthn 客户端时的 Related Origin 校验（拉 `/.well-known/webauthn`） | 启用桌面浏览器 Passkey 后，按需发生 | 你正在登录哪个网站 |
| 更新检查 | 待 K060 决定 | 你在用 keex 及版本 |
| 在线泄露查询 | 关（K032） | 见 §6 |
| Web静态构建与版本资源 | 用户打开其选择的部署时发生；不加载第三方字体/图标/CDN资源 | 访问IP、浏览器与版本请求；不能声称首次访问网站也完全离线 |
| OneDrive交互授权与令牌交换（含Web SPA） | 用户主动启用同步和授权时发生 | 所选Microsoft账号、授权范围、回调/会话元数据；不发送库主密码 |

按需发生的校验应缓存结果，减少暴露次数；启用对应功能时告诉用户会有这类请求。

Web同步连接还受部署CSP和服务端CORS约束，按 ADR-0007 实测；不使用公共代理或要求关闭浏览器安全。首版没有云OCR、AI读库、银行余额抓取、eSIM激活服务器探测或通知内容云端计算。这些不属于已授权联网项。

**不承诺**：隐藏“你在用 keex 同步到某个服务器”这一事实——流量特征和连接的域名可见。

### T9 其他 KDBX 客户端与插件

同一个库可能也被 KeePassXC、KeePassDX 等打开。它们可能丢掉不认识的字段、改写格式，或因缺陷写坏文件。

**承诺**：keex 自己不丢不认识的数据（G0 门槛）；打开时做完整性校验；有祖先快照时三方合并能把差异摆出来。

**不承诺**：阻止别的客户端丢数据。被别人丢掉的字段，keex 只能从库内历史或加密备份找回——前提是还存在。

### T10 供应链、构建与更新通道

依赖包、构建机、发布或更新渠道被投毒。

**承诺**（K060）：依赖锁定版本、生成 SBOM、发布包签名、提供校验和；新增依赖记录许可证和维护情况。发布构建不带调试授权（如 macOS 的 `get-task-allow`）和详细日志；调试构建只能配合合成数据使用（[REAL_DATA_RULES.md](REAL_DATA_RULES.md)）。

**不承诺**：上游被攻破且尚未被公开发现期间的安全。

### T11 旁观者、截图、录屏与任务预览

**承诺**：秘密默认遮罩；切到后台时遮挡任务预览（K019）；读屏软件不自动朗读秘密，验证码变化不反复播报（AC-UX）。

**不承诺**：所有平台都能阻止截图或录屏——各平台能力不同，见 [CAPABILITIES.md](CAPABILITIES.md)。用户主动把秘密显示给别人看，不在防护范围。

### T12 keex 自身的缺陷

对密码管理器来说，最可能发生的事故是**自己把库写坏或丢了数据**，而不是被黑。

**承诺**：G0 无损门槛未过，写入保持关闭；原子保存；写完重新打开校验后才报告成功；有上限的加密备份；遇到无法保证保留的数据就只读。对应关键链 K002 → K003 → K009 → K016。

**不承诺**：没有任何备份时硬件损坏导致的丢失。

### T13 胁迫与社工

**不防。** 被人逼着交出主密码的情况，keex 不提供“伪装库”“紧急销毁”之类的功能，也不暗示有。忘记主密码且没有其他有效密钥材料时无法恢复，这是设计结果，不是缺陷。

### T14 SSH 代理转发到被攻破的远端【桌面】

用户用 `ssh -A` 登录一台跳板机后，那台机器上的 root 或同账号进程可以经转发通道请求 keex 签名。

**它能做**：限时授权期间静默签名；按次确认模式下，转发来的请求和本地请求在确认框里看起来一模一样，用户会照常点确认。

**承诺**：

- 只有**验证**了 OpenSSH 的 `session-bind@openssh.com` 扩展（OpenSSH 8.9 起提供）之后，才显示来源信息。验证是指：用其中的主机公钥验证它对会话 ID 的签名，再核对待签数据里的会话 ID 与绑定的一致。只解析不验证，等于相信对方自报的身份。
- 验证通过时，确认框显示主机密钥指纹和“是否经过转发”；只有在本机 `known_hosts` 里按这把主机密钥找到明文主机名时，才附上主机名。
- 没有经过验证的会话绑定时，确认框必须写“无法区分本机请求和转发请求”。
- 限时授权的文案写明“包括你转发过代理的远端主机”。

**不承诺**：没有会话绑定时识别请求来源；客户端不是 OpenSSH 时提供任何来源信息。

**验收**：AC-SSH；K044、K047；[ADR-0001 §6](0001-flutter-kdbx-architecture.md)。

### T15 Web执行环境、托管通道与同源脚本

攻击者可能替换入口HTML/JS/WASM/响应头，利用XSS、恶意附件、被投毒依赖、浏览器扩展或旧Service Worker；还可能利用多标签、缓存清理、BFCache恢复和页面关闭制造越权或数据丢失。

**承诺（待K070–K072/K081–K088验证）**：

- 只加载固定来源、可核对版本的静态构建，依赖锁定；默认没有第三方脚本/字体/图标、统计或明文后台。执行CSP、嵌入限制、安全文本渲染和附件隔离；不能以Flutter兼容为由无条件放开脚本执行。
- 默认只在当前会话持有解密材料；显式启用的持久缓存仅存KDBX及加密快照。主密码、等效解锁材料、明文字段/索引/附件和同步认证秘密不进浏览器持久存储。同步认证秘密包括 access/refresh token、WebDAV 密码与上传会话 URL，无论有效期长短均只放受控会话内存；仅 K072 明确列明用途、期限和清理点的 OAuth 事务材料可例外，不能混入库密钥。
- 解锁、编辑、保存、同步都绑定epoch和generation；刷新、BFCache/Worker恢复不得复活旧授权。同源标签协调不替代远端条件写入。
- 准确区分内存修改、密文缓存、准备下载、文件回读验证和远端确认。浏览器API不足时只提供安全的新副本导出/只读，不冒充原子写回；配额/驱逐/关闭页面测试覆盖数据丢失反例。
- 新静态构建不得在解锁编辑过程中悄悄接管；未来Service Worker更新先完成安全保存或明确未保存，再锁库切换。

**不承诺**：

- 无法抵御已经控制实际执行代码的托管攻击者、浏览器漏洞或有读取页面权限的恶意扩展。CSP/SRI/校验和不是控制入口HTML后的独立信任根；Worker/WASM也不是秘密防火墙。
- Web只展示部分字段不等于仅解密部分主库；解锁完整KDBX会使该执行环境进入整库信任范围。需要强隔离须用户另建独立库，不能用UI分类代替。
- 浏览器持久化授权保证永不清理、下载已被用户保留、页面关闭事件一定完成保存、关页后精确定时通知，均不成立。
- 普通Web客户端不具备跨网站系统凭据提供者、SSH代理或原生安全存储的等价能力。手机平台安全承诺不能直接迁移到浏览器。

**验收**：AC-WEB、AC-SECRET、AC-SAVE、GW0–GW2；K070–K072、K081/K082/K084/K085/K088。依据见 [研究PV04/PV09–PV15](research/personal-vault-2026-10-16.md)。

### T16 资料关系、维护规则与通知完整性

错误来源可能是恶意导入、其他客户端改写、规则过时、用户误标、时区变化、同步并发或重复通知。风险是绑定关系被替换、停号后失去恢复渠道、重复或错过维护，以及通知暴露个人资料。

**承诺（待K068/K073–K080/K083/K087验证）**：

- 关系与规则进入加密KDBX，使用稳定UUID/规则ID与版本；反向索引可重建。关系不自动授予填充、签名或支付权限；缺失目标不按同名自动替换。
- 换卡/停号先列影响，逐项用户确认后才更新；归档、停用、回收站分开；禁止级联删除凭据。提交前验证所有相关基线和epoch。
- 金额快照及来源/记录时间/可信程度、订阅价格与计费周期、日期+时区/精度、关系和规则组成业务原子组；不同 relationId 的新增也必须满足单一当前付款关系等槽位约束。冲突不按设备时钟自动胜负，不拼接不同版本的事实或半条关系。
- 余额/流量/机构状态只显示明确来源和记录时间；保号依据缺失时保留未知；点提醒不算已充值。月末、闰年、DST、旅行时区和撤销完成有确定规则。
- OS只获取用户同意的最小调度时间、随机ID和通用文案，无标题、机构、号码、金额、条目UUID或激活资料。映射在受设备保护的位置；取消规则/移库清理调度；通知点击需重新授权，不直接完成维护事务。

**不承诺**：不保证用户录入或机构规则永远正确；没有官方确认时不能证明扣费/充值/停号已执行；受OS后台/权限和设备离线影响，不承诺所有提醒准时送达或跨设备恰好一次。通用通知仍会暴露触发时间和“正在使用keex”，这属于用户启用后的最小元数据泄露。

**验收**：AC-VAULT-DATA/REL/LIFE/COMPAT；VT01–VT11、VT17–VT18。资料管理不是自动代办服务。

## 5. 锁库语义

给 K012、K019、K038、K049、K052、K053 的共同契约（【桌面】还有 K044）。

**锁库** = 会话 epoch 加一 + 丢弃派生密钥和已解密对象 + 让所有进程（主程序、扩展；【桌面】还有代理）看到新 epoch。epoch 说白了就是一个只增不减的“会话版本号”：每个操作开始时记下它，交出结果前再对一次，对不上就说明中间锁过库。

**分界点**是 epoch 加一的那一瞬间：此前已经输出的算“锁库前”，此后要输出的一律拒绝。每个交出秘密或能力的操作都必须在**输出前最后一步**再检查 epoch，开始时检查一次不够。

| 操作 | 锁库前已完成 | 锁库时正在进行 | 锁库后发起 |
| --- | --- | --- | --- |
| 显示秘密 | 立即遮盖或退出敏感页面 | 还没渲染的不再渲染 | 拒绝，要求解锁 |
| 复制到剪贴板 | 能确认剪贴板里仍是 keex 写入的那个值时清除；确认不了就不动，避免清掉用户后来复制的内容。用系统的变更计数判断（iOS `changeCount`；【桌面】macOS 同名属性、Windows `GetClipboardSequenceNumber`），不读回内容——iOS 16+ 读剪贴板会弹授权，Android 10+ 后台读不到；Android 怎么判断由 K019 实测确定 | 还没写入的放弃 | 拒绝 |
| 自动填充、系统凭据请求 | 已返回给系统的收不回 | 返回前检查 epoch，不通过则按系统协议返回取消或“需要交互” | 返回“需要解锁” |
| Passkey 注册与断言 | 已返回的收不回 | 签名后、返回前再检查；注册必须已本地持久化才能返回成功 | 拒绝 |
| 【桌面】SSH 签名 | 已发出的签名收不回 | 签名前、写回 socket 前各检查一次，不通过就返回失败 | 拒绝；锁库后代理不再列出任何公钥 |
| 同步 | — | 只传密文的步骤继续；需要解密合并的暂停为“等待解锁合并” | 只传密文 |
| 保存 | 已提交的有效 | **待 K012/K016 决定**，见下文 | 拒绝 |

锁库撞上正在进行的保存，K012/K016 必须在下面两条不变量内选一种做法并写进证据：一是任何时候都不能留下半个文件，二是没有重新打开校验就不能报告“已保存”。无论选哪种，用户都必须被明确告知这次修改是“已保存”还是“未保存”，不能静默丢掉。

其他硬规则：

- 解锁失败、用户取消、KDF 被中断，都不能恢复旧会话。旧 epoch 永久作废。
- 扩展（【桌面】和代理）在处理每个请求前读取最新 epoch，不依赖“主程序会来通知我”。主程序崩溃时，扩展必须安全地拒绝，而不是沿用缓存的授权。
- 对用户的说法：锁库是“从这一刻起不再交出”，不是“收回已经交出的”。

**Web增量**：页面、Worker与同源标签对输出/提交执行同样的epoch校验；广播只能辅助通知失效，不能当作唯一撤权依据。页面隐藏/闲置/显式锁定触发策略独立验证；浏览器不具备原生系统锁屏事件的完整保证，不能伪称等价。重新显示或从BFCache恢复时先验证会话，失效即重新解锁。

**维护与通知增量**：锁库后不解密计算新提醒、不执行关系更新、不记录完成；已获用户同意并交给OS的通用通知可继续触发，这不是保留解密能力。用户关闭通知、移除库或删除规则时清理对应调度；锁库本身不自动撤销这些通用通知。

## 6. 隐私：不是秘密，但不该外泄

- **系统凭据索引**只放显示候选所需的最少信息：账户名、RP ID，以及 iOS Passkey 候选必填的 credentialID 和 userHandle（userHandle 可能是邮箱或账号 ID），不放密码、OTP seed、私钥、主密码或同步令牌。开启时告诉用户这些会进系统索引；停用库时清理（[ADR-0002](0002-mobile-credentials.md)）。
- **日志**默认只记事件码、耗时、字节数。本文件提议：本地日志也不写条目标题、URL、用户名、RP ID 和库文件名，调试模式的例外由 K010 定义且仍不得含秘密。
- **崩溃报告和统计**：keex 自己的默认没有，以后要加必须用户主动开启且不含库内容。系统自带的崩溃上报（Apple 诊断、Windows 错误报告、Android 厂商上报）由系统决定；keex 尽量把自己排除在外（见 T4），但不承诺完全关掉。
- **网站图标**默认不联网获取——每拉一次图标，就等于告诉图标服务“这个人在用哪个网站”。
- **在线泄露查询**默认关闭（K032）；启用后也不得发送完整密码或其完整哈希。

## 7. 维护规则

- 新任务开工时，在证据文件里写明涉及的资产编号（A1–A11）和攻击者编号（T1–T16）。新资料和Web增量仍待独立复核，历史K001证据不得自动覆盖。
- 改动任何“承诺”或“不承诺”，需要独立复核，并同步检查界面文案。
- 新增平台、新增联网功能、新增跨进程接口（例如 CLI、浏览器桥接），先在这里加对应条目（联网的加进 T8 的表），再进实现。
