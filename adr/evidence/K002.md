## 设计决定

- **为什么自己写解码器**：如果用 KeePassXC 同时读候选库写出的文件和原文件，KeePassXC 自己读丢的东西两边都看不见，“无损”结论会是假的。实测证实 KeePassXC 确实会丢数据，见下一节。反过来，解码器也不能只和自己生成的 manifest 比，所以另有一组和 KeePassXC 导出内容的整体对照：14 个可打开样本，除了 KeePassXC 自有元数据和 4.x 附件（它导出时会丢附件内容），两边完全一致。
- **Salsa20 是自己写的**。原因是 cryptography 没有 Salsa20，而 KDBX 3.1 的内层保护流只用它。这按规范实现的是标准算法，不是自创密码学；它只在测试里解密、不加密任何新数据。核对分三层：规范第 9 节的示例向量、eSTREAM Set 1 vector 0、KeePassXC 写的 3.1 库里的受保护值能逐字还原。第三层用到了多个连续的受保护值，密钥流错位一字节都过不了。
- **源 XML 确定性生成**。UUID、时间、SSH/Passkey 密钥都从公开种子派生。好处有两个：含明文私钥的 XML 不用进仓库；测试随时能重建源数据，核对“KeePassXC 导入时改了什么”。OpenSSH 私钥文件是自己拼的，因为 cryptography 导出时的 checkint 是随机数；拼好后用 cryptography 和 `ssh-keygen -y` 都读回来核对过。
- **损坏样本确定性变异，并且只让一项检查拦住**。测试会重跑变异、核对字节一致。改了头部的样本会把其他校验值重新算对（必要时用已知合成密码重算头部 HMAC、重写 HeaderHash），这样缺了哪项检查的实现就会打开哪个样本。需要改密文内 XML 的几个 3.1 样本是用原密钥和 IV 重新加密的。这是做测试数据的工具，不是 keex 的写入实现。

## 做样本时发现的事

KeePassXC 2.7.12 的写库行为和对损坏样本的实测表现，写在[样本说明](../../tests/fixtures/kdbx/README.md)里，这里不重复。对后续任务影响最大的：

- 4.1 下分组和条目 CustomData 的 `LastModificationTime` 会被 KeePassXC 丢掉；4.x 库里的附件会全部被标成受保护。K003 的往返测试里有一步是“参考客户端读取并编辑”，这一步如果用 KeePassXC，这两类差异要记在 KeePassXC 头上。
- `keepassxc-cli rm` 把条目移进回收站时会写 PreviousParentGroup，整库随之从 3.1 升到 4.1。keex 不能假设一个库的版本始终不变，每次写入都要按当时的实际版本处理。
- KeePassXC 比 keex 的规则宽：尾部多出数据和声称 4.2 的库都照常打开；10 万层嵌套会让它段错误；1 TiB 的 Argon2 参数会让它卡 20 秒以上。所以“KeePassXC 能打开”不能当作 keex 也该打开的依据。

做样本和复核中，在解码器自己身上发现并修了这些问题。keex 自己的实现也要过同样的关：

| 问题 | 后果 | 修复 |
| --- | --- | --- |
| 10 万层嵌套的 XML 能解析成功 | 之后递归处理会栈溢出 | `226a15f` 超过 256 层拒绝 |
| DOCTYPE 只查开头 4 KB | 前面塞注释就能绕过 | `226a15f` 查全文 |
| DOCTYPE 按 UTF-8 字节搜 | UTF-16 的 XML 能把实体塞进去并被展开 | `71df88b` 非 UTF-8 一律拒绝 |
| 3.1 先去填充再比 StreamStartBytes | 截断或追加的文件报成“密钥错误”，用户会反复试密码。`226a15f` 只修了不对齐的情况 | `71df88b` 先比开头再去填充 |
| 密钥文件判定和 KeePassXC 有三处不同 | 带 DOCTYPE 的文件报错、“62 位 hex + 换行”被当成 hex、XML 2.0 缺 Hash 放行 | `71df88b` 按 KeePassXC `FileKey.cpp` 对齐 |
| 4.x 先跑 KDF 再核头部 SHA-256 | 改坏的头部也要先烧一遍 KDF | `58e70ed` |

## 复核

复核者是另起的同型号子 agent（独立上下文、只读），**不是人工或第三方复核**。它提了 6 条必须改和若干建议，并用 keepassxc-cli 实际打开过部分损坏样本。

**复核报告原文没有存进仓库，事后也取不回来**（只在当时的会话里）。下表按当时各个提交说明里写的复核意见整理，必须改和建议合在一起列，没有逐条区分。全部已处理：

| 复核提出的问题 | 处理（commit） |
| --- | --- |
| 3.1 在 16 字节对齐处截断或追加，仍报“密钥错误” | 先比 StreamStartBytes 再去填充（`71df88b`）；补 R31-TRUNC-ALIGNED、R31-TRAILING-ALIGNED（`76ed598`） |
| UTF-16 的 XML 能绕过 DOCTYPE 检查 | 非 UTF-8 一律拒绝（`71df88b`） |
| 密钥文件判定和 KeePassXC `FileKey.cpp` 有三处不一致 | 对齐（`71df88b`） |
| “空元素等于没有”对未知元素也生效 | 只对已知元素折叠（`7d8ed2c`） |
| 附件保护标记和附件内容在 manifest 里是同一条，分不出是哪种变化 | 分开报（`7d8ed2c`） |
| 解码器 README 把没有样本验证的密钥文件格式写成“支持” | 补 XML 1.0、32 字节两个样本（`6fa2133`）和不压缩变体（`76ed598`）；README 改为“实现了哪些”，两张缺口表合一（`8efea07`） |
| R41-HEADER-HMAC、R42-VERSION、Twofish 三个样本没有隔离出它们声称要测的检查 | 重做为只有那一项检查能拦住，Twofish 换成 R31-CIPHER-UNKNOWN；逐个验证过补上对应校验值或关掉对应检查后能打开（`76ed598`） |
| 拒绝测试只断言异常类型 | 同时断言异常信息里的原因片段（`76ed598`） |
| 解码器只和自己生成的 manifest 比；KeePassXC 对损坏样本的实际表现没记 | 加和 `keepassxc-cli export` 的对照测试（`76ed598`）；样本表加实测列（`8efea07`） |
| cryptography 没按 AGENTS.md 登记；测试耗时写在多处 | 登记并固定版本；耗时只留本文件（`8efea07`） |

做实测列时另外发现：原 R31-HEADERHASH-MISMATCH 插的是 Comment 字段，KeePassXC 以“不认识字段 1”拒绝，并没有测到 HeaderHash。已改成交换两个头部字段的位置，KeePassXC 现在报“Header doesn't match hash”（`76ed598`）。

修正后没有做第二轮复核。

## 未覆盖与限制

缺口清单只维护一份，在[样本说明](../../tests/fixtures/kdbx/README.md)末尾。影响验收判断的是这几条：

- **AC-KDBX 要求的 Argon2d、Argon2id、ChaCha20 外层加密，都没有样本**，因为 keepassxc-cli 不能选算法。解码器里的 Argon2id 和 ChaCha20 外层路径没有端到端验证；Argon2d 解码器根本不支持。不补齐的话，K003 对这几种组合给不出结论。
- 参考客户端写的样本只有 KeePassXC 2.7.12。AC-KDBX 要求 KeePass、KeeAgent 和目标移动客户端分别记录，这些都还没做。KeeAgent 设置是按格式手写的，没有用 KeeAgent 本体验证过。
- 4.x 的压缩炸弹和 XML 攻击样本没做，只做了 3.1 的。
- M01 的“多凭据”只覆盖了两个不同 RP 的 Passkey，同一 RP 下的多个凭据没有样本。
- 自动秘密扫描脚本没做（[REAL_DATA_RULES](../REAL_DATA_RULES.md) 已如实更新）。
- 复核只有同型号子 agent，没有人工独立复核。按 AGENTS.md，协议兼容类工作要独立复核才能进 DONE。
