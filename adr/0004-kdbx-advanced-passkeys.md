# ADR-0004：高级 KDBX 属性、附件与 Passkey 互通

日期：2026-10-12。状态：**字段与行为契约；兼容样本及签名互通尚未实测**。Rxx 引用见 [调研](research/mobile-sync-2026-10-12.md)。

## 1. 不把 KDBX 压扁成五个字符串

| 数据 | 读取/保留要求 | keex 首版编辑与展示 |
| --- | --- | --- |
| 标准字段与自定义属性 | 名称、值、受保护标志、未知属性均保留 | 普通字段可编辑；秘密默认遮罩；协议字段用专用编辑器 |
| 分组/UUID/标签/图标 | 层级、标识、组设置、自定义图标保留 | 类型是投影，不以分类改写分组 |
| 时间/到期/使用信息 | 创建、修改、访问、到期与 Expires 等语义按支持格式保留 | 到期状态可展示，不把访问时间当同步版本 |
| History / DeletedObjects | 旧字段、旧附件引用、删除时间均保留 | 版本恢复、回收站；清理需显式确认 |
| 附件/二进制池 | 内容、命名、引用及所有历史引用保留 | 主程序导入/预览/导出；扩展不加载附件预览 |
| CustomData / 扩展信息 | 已知未知都进入无损比较 | keex 的 UI 元数据独立命名空间；未知项只读 |
| Auto-Type / URL override / 字段引用 | 原设置保留，不能丢弃 | 移动端不自动执行命令或宏；引用解析限制递归/循环 |
| OTP / KeeAgent / Passkey | 分别识别协议字段和保护语义 | 不认识的记录保留，不能冒充可用凭据 |

KDBX 加密容器与字段内层保护是两层概念：未标记 Protected 的普通字段仍在加密文件中；Protected 不构成另一套访问权限或独立主密码。公开外层头部不放秘密；内层受保护字符串改写要正确重建保护流。[R14]

未知字段原样保留指**语义和保护属性无损**，不是将旧内层密文剪贴到新流中。保存闸门必须覆盖含未知受保护字段、历史和字段顺序变化的样本。核心库若无法表达某项数据，禁写该库并报告，不默默删字段后保存。

## 2. 附件不是独立云盘资源

默认把附件放在标准 KDBX 内，由密码库一并加密与同步；不另存明文图片/私钥到 OneDrive，再在条目里放公开 URL。KDBX 4 的二进制池与 XML 引用、3.x 的相应编码路径分别测试，不用一种格式的保存方法覆盖全部版本。[R14]

附件设计包括名称、类型提示、字节大小、归属条目、当前/历史引用以及操作状态。删除当前附件只移除当前引用；历史仍引用时不能回收底层二进制。相同名称不等于相同内容，摘要用于去重/比较，不是替代库完整性验证。

iOS 导入使用系统文件/照片选择器的最小授权；用户确认后进入加密保存事务。默认不生成可被系统搜索的明文缩略图。预览优先受控内存；必须使用临时文件/Quick Look 时应用文件保护、受限位置、生命周期清理和重启清扫，不宣传可彻底擦除 SSD 残留。外部“分享/打开”是秘密离开 keex 的动作，须单独提示。

配额包括单附件、累计附件、库总量和历史增长，值由 POC 校准。超大既有附件先保证不损坏和可解释的只读/能力降级；不能为了让扩展正常注册而自动删除。大库在核心可能仍需完整解析，不能以“流式 UI”假装不存在 KDF 和解密对象的峰值内存。

## 3. Passkey 在 KDBX 中采用生态适配层

KDBX 本身不定义统一的 Passkey 条目类型。Monica、KeePassXC 等源码提供了可参考的 `KPEX_PASSKEY_*` 约定；这些是客户端生态协议，不是 KeePass 官方为所有软件保证支持的新格式版本。[R08,R15]

| 规范化含义 | 优先兼容字段 | 写入/校验要求 |
| --- | --- | --- |
| 用户显示名 | `KPEX_PASSKEY_USERNAME` | 与 opaque userHandle 分开；不能因为显示名为空就抹掉已有凭据 |
| RP ID | `KPEX_PASSKEY_RELYING_PARTY` | 专用解析与匹配，保留原始导入证据；不能随手改成任意 URL |
| 凭据 ID | `KPEX_PASSKEY_CREDENTIAL_ID` | 规范化为字节；兼容编码是表示层，不可改变身份 |
| 用户句柄 | `KPEX_PASSKEY_USER_HANDLE` | 不透明字节，不能替换成邮箱；受保护存储策略 |
| 软件私钥 | `KPEX_PASSKEY_PRIVATE_KEY_PEM` | 正确解析 PKCS#8/算法，Protected；不传给普通 UI 字段编辑器 |
| 备份标志 | `KPEX_PASSKEY_FLAG_BE` / `KPEX_PASSKEY_FLAG_BS` | 按规范与导入来源处理；不是“绿色同步图标”的直接拷贝 |

旧客户端还可能出现 `KPXC_PASSKEY_USERNAME`、`KPEX_PASSKEY_GENERATED_USER_ID` 和不同 marker。不能仅凭名字把 GENERATED_USER_ID 当作 userHandle；要按来源实现解码 profile。新写遵循验证过的现代映射，旧数据保留别名及其关系；冲突或未知编码进入只读识别状态，不以猜测的 normalize 后回写。[R15]

分类检测与实际可用性分开：遇到某个 KPEX 字段可归入“疑似通行密钥”；只有私钥可解析、算法可用、ID/handle/RP 等参数一致，才成为可签名候选。私钥不存在的外部硬件引用只能说明用途，不声称导入成功。

### 多个 Passkey 与登录账户

读取时保留现有混合条目（登录密码 + 一组 KPEX）。新建多个 Passkey 时采用**每个凭据一个标准 KDBX 条目、一组兼容字段**，可用 `keex.parentEntryUuid` 等非秘密关联元数据组织到同一账户。两个网站账户、多个 credentialId 不按域名或用户名去重覆盖。

逻辑账户可以聚合多个条目，标签页仍是视图而非复制秘密。同一字节身份的重复导入应提示保留/关联；同 credentialId 不同私钥属于安全冲突。未知客户端不理解关联元数据时仍能独立读取每条凭据。

绑定身份使用 keex 本机 VaultBindingId + 标准条目 UUID；不要假设所有 KeePass 客户端都提供同一个官方“库 UUID”。复制/导入文件后的绑定合并需要用户确认，不能用同名文件推断。

## 4. 软件认证器与设备密钥的区别

跨设备可用的软件 Passkey 需要把可恢复的私钥材料保护在 KDBX 内。Secure Enclave/Keystore 的不可导出设备 key alias 不能作为跨设备的私钥内容；OS 密钥可以保护本机解锁材料，但不能用“同步了 alias”声称另一台设备可以签名。

共享认证器候选优先评估 `1Password/passkey-rs` 的 authenticator 与 CredentialStore 抽象；自定义存储接 KDBX，平台桥接提供已验证的请求。不是把供网站服务器验证登录用的库直接当作密码管理器签名器。候选算法、输入 hash 支持、授权回调、存储事务和许可证必须逐项 POC；未实现算法不在 UI 标支持。[R16]

## 5. 创建、使用与系统识别

创建：接收正式请求 → 校验调用方和参数 → 用户确认网站/账户/目标库 → 认证 → 生成材料 → 标准字段编码 → **本地 KDBX 原子持久化并校验** → 标记/更新系统索引 → 返回注册响应 → 异步云同步。

不能先返回公钥成功再等 Flutter 主程序未来有空写库；也不能把只存在内存中的密钥称为已保存。扩展可授权但库只读、并发版本失效或资源不足时，在系统允许范围内恢复/取消，不让网站记住一个本机已丢失的私钥。

断言：解析正式请求 → 找到当前库/RP/credentialId 候选 → 完成必要用户存在/验证 → 按规范构造 authenticatorData 和签名 → 输出前检查撤权及版本 → 返回系统。签名针对原始 clientDataHash 的合法协议输入，不重新生成网页 challenge。

互通要求固定 credentialId/userHandle 字节不变、正确算法与签名编码、RP/hash/用户验证/计数和备份标志策略一致。导入不伪造硬件 attestation，不擅自把未知 flags 当已备份。provider 成功返回与网站最终接受并非同一事件，缺少网站回执时不自动删除本地新记录。

## 6. 凭据交换、导出与兼容矩阵

FIDO CXF/系统 Credential Exchange 是可选迁移通道，不替代 KDBX 同步。Apple iOS26 与 Android Credential Transfer 的能力和 SDK 成熟度单列；用户选择、设备认证、受信任对端、临时数据范围、原子导入与失败恢复都验证后再开放。[R17,R18]

不要用 CSV、二维码或普通 JSON 默认导出 Passkey 私钥。旧 `.passkey` 文件或其他明文格式仅在明确迁移授权下处理，导入后临时材料按限制清理，不能悄悄加入云端自动备份。

验收矩阵至少包含：KeePassXC ↔ keex Android ↔ keex iOS；Monica 的 KDBX 兼容模式；KeePassium 的库内 Passkey；只支持普通 KDBX 的客户端往返保留。每个格子分别记录“结构保留、可创建、可认证、再编辑、异常不丢数据”，且必须写客户端发行版本/源码快照。当前这些格子全部待实测，不能因为同字段前缀就标绿色。
