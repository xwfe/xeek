# ADR-0001：Flutter + KDBX 跨平台密码管理器

日期：2026-10-12。状态：**产品边界已确定；核心库和原生扩展实现需通过 P0 实验后批准**。

细化设计以 [ADR-0002](0002-mobile-credentials.md)、[ADR-0003](0003-cloud-sync.md)、[ADR-0004](0004-kdbx-advanced-passkeys.md) 为准：iOS与Android同期验证，OneDrive进入P3；高级字段/附件/Passkey在写入门槛中验证。

## 1. 已确定与未确定

已确定：Flutter 主界面，五端目标；中文优先、五项导航；本地优先；KDBX 唯一权威数据；SSH Agent/KeeAgent 兼容；系统自动填充；TOTP/恢复码/Passkey；可选自托管同步。

未确定：具体 KDBX 写入库、Rust/Dart 边界最终落点、各端最低系统版本、浏览器扩展实现路径、通行密钥跨客户端字段映射、发行许可证。它们不能由演示稿或一个 pub/crates 包的标签代替验证。

## 2. 整体分层

```text
Flutter 应用（Dart）
  ├─ 五项导航、设计系统、本地化、可访问性
  ├─ 业务视图模型：条目摘要/搜索/编辑/同步状态
  └─ 类型化能力接口（不暴露完整库、长期主密钥）
          │
共享领域与安全核心（优先评估 Rust，P0 决策）
  ├─ vault-core：KDBX 读写、会话、条目、历史、附件、内存生命周期
  ├─ credential-core：生成器、TOTP/HOTP、通行密钥记录与签名策略
  ├─ sync-core：版本、三方合并、冲突、原子写入、恢复
  └─ agent-core：SSH agent 协议、授权、超时、锁库撤销
          │
平台适配与进程边界
  ├─ Swift：Apple Keychain / 本地认证 / 文件授权 / 凭据扩展
  ├─ Kotlin：Keystore / 生物认证 / AutofillService / CredentialProviderService
  ├─ 桌面：本地 IPC、剪贴板、托盘、会话锁定、浏览器桥接
  └─ 同步 provider：本地文件、WebDAV、OneDrive；分别验证授权与最终提交
          │
加密 .kdbx 文件 + 加密版本快照；OS 安全存储仅放设备授权材料
```

Rust 有利于共享协议与控制密钥生命周期，但并不自动保证安全；Flutter/Dart、系统框架和 FFI 仍可能产生短期副本。首选 `flutter_rust_bridge` 验证 Flutter 桥接，原生扩展用稳定 C ABI/合适绑定调用同一核心；这不是承诺一份 Dart 引擎可运行于所有扩展。依据 S02–S04、S10。

暂定目录（尚未创建应用代码）：`apps/keex/`、`packages/keex_platform/`、`crates/vault_core/`、`crates/credential_core/`、`crates/sync_core/`、`crates/agent_core/`、`native/apple/`、`native/android/`、`extensions/browser/`、`tests/fixtures/`。初期可合并少量 crate，按边界而不是按文件数量拆分，不先造通用插件市场或微服务系统。

## 3. KDBX 格式与库选型门槛

官方当前最新格式是 **KDBX 4.1**，新库默认此格式；读取目标覆盖 3.1/4.0/4.1 的约定测试集合。旧库升级必须备份、解释兼容影响、用户确认；不默默降级/升级或重建全库。更高的未知版本默认只读或拒绝，不能“尽力读完再覆盖”。[S01]

候选：Rust `keepass-rs`；Dart `kdbx.dart` 作为对照。当前 Rust 官方描述仍将 4.1 写入标为实验性，Dart 宣称 3.x/4.x 支持也不等于未知字段和插件数据无损。因此必须先执行同一组黄金样本往返、跨客户端二次编辑、附件/历史/自定义字段保护测试。[S03,S04]

裁决顺序：可复用成熟实现 → 以少量可审计补丁补齐并回馈上游 → 更换符合要求的实现。若两者都未达标，阶段停在只读验证，重新提交有成本/许可证分析的 ADR；不得为追赶 UI 进度自写一套加密格式。任何 GPL 代码移植/链接需先核对实际许可证义务，不把“参考”当成可随意复制。

无损不是密文字节相同。每次保存随机盐/IV 可变化；比较解密后的语义、二进制附件摘要、UUID、历史、引用、属性、保护标志及插件数据。尤其未知的 `Protected` 字段：需要消费正确的内层流位置并重新保护，不能原样粘贴旧内层密文到新的流顺序。[S01]

标准字段保持 Title/UserName/Password/URL/Notes、Group、UUID、Tags、History、DeletedObjects、附件、CustomData。类型/展示偏好使用有版本的命名空间数据（暂定 `keex.*`，实验确认具体字段位置）；秘密使用受保护字段/受控附件，不存公开头部。无法编辑的第三方配置仍应无损保留，遇到不可保证保留的数据禁止写入。

## 4. 数据模型与能力接口

导航类型与存储实体解耦：同一 `EntryId` 可以产生 PasswordView、VerificationView；不要为 tab 复制条目。分组和类型正交，不因为移分组就变成银行卡。外部无类型条目默认归普通条目，推断不回写；用户明确改类型才落盘。

证件/银行卡为普通 KDBX 条目的受保护扩展字段与附件。手机号、证件号、卡号、CVV、PIN、恢复码、OTP seed、私钥均视为秘密；CVV/PIN 不默认要求填写，不默认复制/自动填充。外部安全密钥只记录说明或引用，不声称导出硬件私钥。

拟定核心接口：`openVault`、`unlock`、`lock`、`listSummaries`、`readFieldForDisplay`、`applyEntryPatch`、`generateSecret`、`getOtp`、`requestSignature`、`prepareSave`、`commitSave`、`planMerge`、`resolveConflict`。接口输出类型化错误和能力状态，不向日志返回原始密码库对象。会话句柄带本机 VaultBindingId、generation/epoch，条目使用标准 UUID；不假设所有客户端提供同一个官方库UUID。锁定、切库、撤权后旧句柄失效。

列表持有最小摘要；秘密读取/复制/签名均按用途授权。复制优先核心至平台剪贴板，减少跨 Dart 往返；显示时不得声称可保证擦除 Dart 不可变字符串。UI 状态恢复和系统任务预览不得持久化敏感页面。库内搜索只在解锁会话的内存中维护，磁盘不落明文索引。

## 5. 解锁、加密写入与备份

主密码 + 可选密钥文件为首个可交付路径。新库 Argon2id 参数按性能与最低安全策略校准，必须考虑手机和扩展内存预算；文件里的 KDF/cipher 原样识别并准确显示。不写死“64 MB 就安全”或把 PBKDF2 当作 KeePass 默认。AES-256-CBC+HMAC 与 ChaCha20 按官方 KDBX 规范实现/验证，不改成 AES-GCM 容器。[S01]

密码库外层 MAC/完整性检查不通过不得接受内容或写回；限制文件/附件/XML 深度、KDF 极端参数和压缩炸弹，不能让任意下载文件耗尽内存。明文导出单独警示与二次授权，不能保证底层 SSD 安全擦除，默认不开明文自动备份。

保存事务：校验读时版本 → 构造新库 → 同目录受限权限临时文件 → 刷新与可重开验证 → 原子替换 → 确认保存 → 更新版本快照。失败不得毁坏旧文件；同目录原子替换不可用的文件 provider 使用经过测试的替代协议/只读降级，不泛化 POSIX rename 到云盘文件系统。

自动保留有上限的**加密**备份和合并祖先；恢复是重新打开校验后的副本，不是在原文件上盲目覆盖。库主密码/密钥文件更换需备份恢复演练，避免新旧设备互相回写旧密钥配置。

生物识别通过系统安全存储封装的本机快速解锁材料实现，不上传生物特征、不将短 PIN 当独立 KDBX 主密钥。设备锁/生物录入变更/系统权限撤销后快速解锁失效并回退完整密钥。Keychain、Keystore、Windows 设备保护及 Linux Secret Service 的保障不同，能力检查后展示而非统一承诺。首次解锁和定期再验证规则应可解释。

## 6. SSH Agent / KeeAgent

KeeAgent 是 KeePass 2.x 插件，可自充代理或对接外部代理；Flutter 不能直接加载它。keex 的目标是**保存兼容数据 + 实现代理协议与用户流程**，不是兼容整个 KeePass .NET 插件 ABI。[S05]

优先实现自有受控代理：macOS/Linux Unix socket，`SSH_AUTH_SOCK` 定位；Windows OpenSSH 管道/路由需 P0 验证，必须处理系统 ssh-agent 占用、ACL 和当前用户隔离，不能启动后覆盖系统服务。Pageant 作为后续兼容；移动端不承诺向其他任意终端 App 暴露常驻 SSH 代理。

先支持 Ed25519、现代 RSA/SHA-2，ECDSA/PPK 等按测试矩阵扩展；不为兼容启用 SSH1/DSA/弱签名。导入 KeeAgent 附件、私钥口令及配置须用真实合成样本确认字段格式；保留外部私钥文件引用，不擅自把路径指向的内容拷进库。SSH 签名不需要把私钥写到临时磁盘。

授权策略：每个密钥显式允许加入代理；按次确认或有期限授权；签名开始与输出前检查同一会话 epoch；锁库、系统锁屏、到期、退出时停止服务/撤销钥匙和在途请求。普通代理协议不可靠携带远端主机身份，不能显示未经验证的“已授权 example 主机”；只有经过 OpenSSH 会话绑定/目的地约束验证才支持目的地限制。[S09]

**对接外部代理并加载私钥**会把私钥交给其他进程，无法保证 keex 锁定后对方也清除；不作为默认方案。若后续支持，必须独立告知、可撤销、明确权限边界，不能沿用自有代理的强锁库保证。签名日志只留最小事件/结果，不记录私钥、完整待签数据或认证载荷。

## 7. 验证与系统凭据提供者

TOTP/HOTP 依照 RFC 测试向量；支持算法/位数/周期与计数器，扫码在本地解析。HOTP 取码和递增需事务，跨设备冲突不能当普通数字字段自动合并。恢复码按条记录，明确标记使用不会自动通知网站。

Passkey 分成三层：KDBX 存储且无损互通；受审查的 WebAuthn/签名核心；操作系统/浏览器调用入口。保存一个 Passkey 字段不等于可替网站登录。需正确处理 RP ID、origin/调用方校验、challenge、userHandle、credentialId、算法、用户验证、取消、备份标志/计数策略；不自行编造认证元数据。首版软件通行密钥与硬件不可导出凭据是不同类型。

Android 14+ 通过 `CredentialProviderService` 提供密码和通行密钥，旧版密码自动填充走独立 AutofillService；服务必须能在主 Flutter 界面不存活时按授权冷启动。[S06]

Apple 使用 Credential Provider Extension / AuthenticationServices，由 Swift 原生扩展处理系统请求，再调用共享核心；App Group、Keychain access group、扩展内存、锁定状态以及双进程写库要真机验证。具体最低 OS 按所用 API availability 确定，不照搬“支持 passkey 登录”的 Flutter 插件系统要求。[S07]

桌面浏览器填充采用经过配对和身份校验的本地桥接/浏览器扩展；不能开启无认证 localhost HTTP API。原生操作系统 Passkey provider 另外评估，不把桌面全端系统注册写成首版完成。KeePassXC 的 Passkey 浏览器方案可参考，但不是声称现有 KeePassXC 扩展天然可连接 keex。[S08]

兼容性测试涵盖 KeePassXC/KeePassDX 等实际字段及导入导出；KDBX 可扩展不意味着所有客户端会理解这些字段。互通未验证时保留原始数据并关闭相应写入/注册功能。

## 8. 同步策略

KDBX 本地文件为唯一数据源；自托管是“自己选择密文文件存储”，不是强制运行账户后端。首个云同步阶段同时覆盖 WebDAV 与 OneDrive；每库只启用一个双向源，iOS文件提供者与云直连不竞争写同一对象。用户历史提及的小程序/Web 保留为后续受限入口研究，不承诺运行原生 SSH 或拥有完整私钥库，不作为当前五端安全核心的先决条件。

Provider 只处理加密对象、版本号/ETag、条件读取写入、超时重试。服务器凭据存设备安全存储，避免仅存于尚未能下载的同一库造成首次同步循环依赖；不把同步访问令牌和主密码混为一谈。跨源重定向不转发认证头；TLS 错误默认拒绝。

WebDAV 有可靠 ETag/If-Match 时使用条件写入。缺少/不遵守强版本条件时，不无条件覆盖远端，进入安全冲突副本模式；服务器的 LOCK 不是唯一安全依据。移动后台可传输密文，不在未授权锁定状态下解密合并。

合并使用已记录加密祖先 + 本地 + 远端三方比较：不同条目可合并；同条目字段分叉按规则/显式选择；删除与编辑、附件、分组移动、历史、保护标记都需处理。**不能仅取最后修改时间较新者**，也不能拿设备时钟作为唯一版本依据。KeePass 原生同步语义是参考，不冒称它已有相同的三方算法。[S11]

状态：仅本地、待上传、下载中、等待解锁合并、冲突待处理、已同步、失败重试。只有条件提交成功才显示已同步；同步不是备份、TLS 不是文件端到端加密、旧密文副本也不能被远程撤销。

## 10. 首版范围与明确不做

基础：多库创建/打开/锁定、搜索/分组/标签/收藏、类型模板、受保护字段、附件、历史/回收站、生成器/OTP、导入导出、加密备份、冲突安全同步、原生填充、安全检查、设置、跨平台打包。SSH 与 Passkey 是正式产品目标，试用阶段可以分批，但功能缺失必须标明。

不默认引入：Vaultwarden 协议后端、账户注册、团队 RBAC/在线共享链接、支付功能、钱包交易、秘密交给 LLM、通用第三方插件执行、暗网监控营销、六位 PIN 独立解密、在所有平台常驻代理的承诺。后续 provider 可扩展，首版只用内置可信适配；自动化/CLI 必须设计按条目按用途授权，不能给模型一个 dump-vault 接口。
